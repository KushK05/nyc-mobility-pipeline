# Airflow (Astro Runtime 3)

Image: `astrocrpublic.azurecr.io/runtime:3.3-12-python-3.12`, which ships
**Airflow 3.3.2** on Python 3.12. It was the newest Astro Runtime 3.x on
2026-11-14 (no Runtime with Airflow 3.4 was published yet). The DAG tests run
locally against Airflow 3.4.0; `route_on_tests` falls back to
`dag_run.get_task_instance` when `ti.get_task_states` is missing, and stops the
run if neither is available.

This folder is the Astro project. It was hand-written instead of generated by
`astro dev init`; the committed `Dockerfile`, `requirements.txt`, `packages.txt`,
`docker-compose.override.yml`, `dags/` and `include/` are all it needs.

DAG: `nyc_mobility_pipeline` (`dags/nyc_mobility_pipeline.py`), monthly from
2024-01 to 2024-06 with `catchup=True` and `max_active_runs=1`. Each run loads the
month given by its logical date (`{{ ds }}`):

```
check_source_available -> load_taxi_trips --------------------------------+
                       -> choose_weather_path -> sync_weather_airbyte --+ |
                                              -> load_weather_python ---+-> weather_loaded
[load_taxi_trips, weather_loaded] -> dbt_seed -> dbt_run -> dbt_test -> route_on_tests
route_on_tests -> refresh_chatbot_metadata -> log_run_summary   (dbt_test succeeded)
               -> alert_and_stop                                (dbt_test failed)
```

## Start it

1. Put a BigQuery service-account key at `airflow/include/gcp-key.json`
   (git-ignored). The image points `GOOGLE_APPLICATION_CREDENTIALS` at it.
2. Create `airflow/.env` (git-ignored) with the cloud settings:

   ```
   GCP_PROJECT_ID=your-gcp-project-id
   BQ_LOCATION=US
   # optional: Slack incoming webhook for failure alerts
   SLACK_WEBHOOK_URL=
   ```

3. Install dbt packages once into the mounted project (it is bind-mounted, so
   `dbt_packages/` from the host is reused): `cd dbt/nyc_mobility && dbt deps`.
4. From this folder: `astro dev start`. The UI is at http://localhost:8080.

`docker-compose.override.yml` mounts `../dbt/nyc_mobility` at
`/usr/local/airflow/include/dbt` (`DBT_PROJECT_DIR`) and `../chatbot` at
`/usr/local/airflow/include/chatbot`, so `refresh_chatbot_metadata` writes
`chatbot/metadata.json` in the repo (override with `CHATBOT_METADATA_PATH`).

## Connections

| Conn id           | Type    | Settings                                          | Used by                  |
|-------------------|---------|---------------------------------------------------|--------------------------|
| `tlc_cloudfront`  | HTTP    | host `https://d37ci6vzurychx.cloudfront.net`      | `check_source_available` |
| `airbyte_default` | Airbyte | host `host.docker.internal`, port `8000` (+ auth) | `sync_weather_airbyte`   |

`airbyte_default` is only needed when the `use_airbyte_weather` Variable is `true`.

```
astro dev run connections add tlc_cloudfront --conn-type http \
  --conn-host https://d37ci6vzurychx.cloudfront.net
# only when use_airbyte_weather=true
astro dev run connections add airbyte_default --conn-type airbyte \
  --conn-host host.docker.internal --conn-port 8000
```

## Variables

| Variable                        | Default | Meaning                                                    |
|---------------------------------|---------|------------------------------------------------------------|
| `use_airbyte_weather`           | `false` | `true` routes weather through Airbyte instead of Python    |
| `airbyte_weather_connection_id` | none    | Airbyte connection UUID; required only when the above is `true` |

```
astro dev run variables set use_airbyte_weather false
```

Variables are read inside tasks only, so parsing the DAG needs no metadata DB.

## Backfill

With `catchup=True`, unpausing the DAG schedules every month from 2024-01 to
2024-06, one at a time. To (re)run a range explicitly:

```
astro dev run backfill create --dag-id nyc_mobility_pipeline \
  --from-date 2024-01-01 --to-date 2024-06-30
```

or use the UI (DAG page, "Trigger" then "Backfill"). Loads are idempotent per
month (delete-then-load for raw tables, `insert_overwrite` partitions in dbt), so
reruns are safe.

## Failure handling

- Every task except `dbt_test` and `alert_and_stop` retries twice (a failing dbt
  test is deterministic, so `dbt_test` has `retries=0`); on final failure `nyc_mobility.alerts.on_failure_callback`
  logs `PIPELINE FAILURE dag=... task=... run=... url=...` and posts to Slack
  when `SLACK_WEBHOOK_URL` is set.
- `dbt_test` ending in any state other than success (failed, or upstream_failed
  when an earlier task broke) routes to `alert_and_stop`, which alerts with the
  observed state (`pipeline stopped for month ...: dbt_test state=...`) and fails
  the run without retrying, so the chatbot metadata is never refreshed from bad data.

## Tests

From the repo root: `.venv/bin/pytest tests/test_dag.py -v` parses the DAG with
`DagBag` (no cloud config, no metadata DB) and unit-tests the callables.
